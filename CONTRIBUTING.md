# Contributing to Orquestrum

Welcome! This repo is the **canonical source** of the Orquestrum
framework. Files here are not consumed directly by AI tools — they're
converted to per-tool packages by `orquestrum convert`. Edits go in
`agents/`, `skills/`, `docs/`, `orquestrum/`, and `ui/`.

> Architectural overview: [`CLAUDE.md`](CLAUDE.md). Read it first if
> you've never touched the project.

---

## Development setup

```bash
git clone https://github.com/johnt1000/orquestrum
cd orquestrum
make dev
```

`make dev` runs `uv tool install --editable .` (so the `orquestrum`
binary is on `$PATH` and points at this clone) and `uv sync --extra ui
--extra webview` (so the FastAPI console and the optional pywebview
window are both available).

Verify with:

```bash
make doctor   # prints runtime, extras, integrations, registry, cwd
```

If something is red, the line below it tells you the exact fix command.

## Daily workflow

```bash
make lint          # validate agents and skills (run before convert)
make convert       # regenerate integrations/ for all tools (no provider)
make convert-dry   # inventory + cost projection, no files written
make web           # FastAPI console at http://127.0.0.1:7700
make test          # uv run pytest (placeholder until Onda 4)
```

The CLI surface is documented under `orquestrum --help` and per
subcommand (e.g. `orquestrum convert --help`). Each subcommand's
`--help` ends with an `Examples:` block.

> Always run `lint` before `convert`. Lint exits 1 on errors.

Configured in `.pre-commit-config.yaml`:

## Adding a new agent or skill

1. Create the file with valid frontmatter (required: `name`,
   `description`).
2. Use only canonical paths in the body: `docs/`, `skills/`,
   `./references/`, `./assets/`. Never tool-specific prefixes.
3. Run `orquestrum lint` — must pass with zero errors.
4. Run `orquestrum convert --all` to regenerate integrations.
5. Commit. The kebab-case slug is computed automatically by
   `orquestrum.lib.paths.name_to_kebab` from `name:` — no manual
   rename needed.

Skills remain as documentation (not registered as agents in any
adapter). Orchestrators read `skills/<slug>/SKILL.md` at runtime and
follow the workflow inline.

## Adding a CLI command

The CLI is an argparse tree rooted at `orquestrum/cli.py`. Each
subcommand lives in `orquestrum/commands/<name>.py` and exposes a
`register(sub)` function. There are two flavors:

### Native command (recommended for new work)

A native command implements its handler directly. Use this when the
command's logic is small and lives entirely inside the package.

**Reference example:** [`orquestrum/commands/doctor.py`](orquestrum/commands/doctor.py).

Skeleton:

```python
"""orquestrum hello — say hi (example)."""
from __future__ import annotations
import argparse


def register(sub: argparse._SubParsersAction) -> None:
    p = sub.add_parser(
        'hello',
        help='Print a friendly greeting.',
        formatter_class=argparse.RawDescriptionHelpFormatter,
        epilog=(
            'Examples:\n'
            '  orquestrum hello\n'
            '  orquestrum hello --name Jonatas'
        ),
    )
    p.add_argument('--name', default='world', help='Name to greet')
    p.set_defaults(handler=_handler)


def _handler(args: argparse.Namespace) -> int:
    print(f'Hello, {args.name}!')
    return 0
```

Then register it in `orquestrum/cli.py` (`_build_parser`):

```python
from orquestrum.commands import (
    convert, install, …, doctor, hello,
)
…
hello.register(sub)
```

### Wrapper command (for legacy `python -m` invocations)

A wrapper forwards `args.passthrough` to a `main()` function under
`orquestrum/core/`. Use this when the heavy logic already exists as a
script-style module (lots of flags, prints, etc.) and you want to
expose it via `orquestrum X` without rewriting.

**Reference example:** [`orquestrum/commands/convert.py`](orquestrum/commands/convert.py)
+ [`orquestrum/core/convert.py`](orquestrum/core/convert.py).

The wrapper sets `add_help=False` so `-h` is forwarded to the wrapped
script's argparse, which keeps a single source of truth for flags.
Make sure the underlying `main(argv)` declares its own
`description=` and an `epilog=` with `Examples:`.

### Conventions

- Every subcommand's help text must include an `Examples:` block.
- Path arguments are spelled `--target` (consistent across `install`,
  `deps`, `web`).
- Destructive operations need `--dry-run` or `--check` (see
  `uninstall --dry-run`, `update --check`).
- Long-running operations should print `[k/N] item` per step (see
  `convert --all`).

## Adding a web route

The console is a FastAPI app under `ui/`. See [`ui/README.md`](ui/README.md)
for the architecture overview. Adding a route is four steps:

### 1. Create the route file

`ui/routes/hello.py`:

```python
"""hello.py — example route showing the FastAPI + Jinja pattern."""
from __future__ import annotations
from fastapi import APIRouter, Request
from fastapi.responses import HTMLResponse

router = APIRouter(prefix='/hello')


@router.get('', response_class=HTMLResponse)
async def show(request: Request) -> HTMLResponse:
    templates = request.app.state.templates
    cfg       = request.app.state.config
    return templates.TemplateResponse(
        request, 'hello.html',
        {'name': 'world', 'is_framework': cfg.is_framework},
    )
```

### 2. Create the template

`ui/templates/hello.html`:

```html
{% extends "base.html" %}
{% block title %}Hello{% endblock %}
{% block content %}
<h1>Hello, {{ name }}!</h1>
<p>Mode: <code>{{ mode }}</code> · framework? {{ is_framework }}</p>
{% endblock %}
```

`mode`, `orq_root` and `request` are injected as Jinja globals — you
get them for free in any template that extends `base.html`.

### 3. Register the router

In `ui/server.py`, inside `create_app(...)`:

```python
from ui.routes import …, hello
app.include_router(hello.router)
```

### 4. (Optional) link from the home page

In `ui/templates/home.html`, add a card under `home-cards`. The home
page is the canonical place for top-level wayfinding.

### Conventions

- One `APIRouter` per feature, with a `prefix=` matching the URL.
- HTML responses go through `templates.TemplateResponse(request, …)`
  so the global Jinja context (mode, orq_root, request) is available.
- For destructive POST forms, set `data-confirm="…"` on the form;
  the inline JS handler in `base.html` will prompt before submit.
- For long-running POST handlers (>2s), submit an async job via
  `ui.lib.jobs.submit(...)` and return
  `RedirectResponse(f'/jobs/{job.id}', status_code=303)`. The
  `/jobs/{id}` page handles polling and rendering automatically.
- Read-only data helpers belong in `ui/lib/` — keep route handlers
  thin.

```bash
git pull

```

Or via the CLI:

```bash
orquestrum update --self  # detects source install → git pull + convert --all
```

## Commit style

Short imperative subject line, no period. Reference the area in a
prefix when helpful:

```
feat(cli): add orquestrum extras command
fix(convert): handle missing frontmatter name field
feat(ui): R14 Onda 2.1 — async job runner with HTMX polling
docs: update installation section
```

When a commit ships part of a roadmap item, mention the item id (e.g.
`R14 Onda 2.1`) so the ROADMAP and the history stay aligned.
